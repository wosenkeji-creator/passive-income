## 分发渠道
- 渠道：Apify Store
- 自然发现流量来源：Apify Store 站内搜索 + 平台自带买家池。**不需要自己宣传**，这是选它的唯一理由。
- 抽成 / 费用：平台抽 **20%**，且**平台成本（计算单元 + 代理流量）从开发者这侧扣**
  官方公式：`profit = (0.8 × revenue) − costs`
- 免费窗口：Creator Plan 约 $1/月，含约 $500 平台用量额度，**仅限前 6 个月**
  → 这个 6 个月天然就是验证期限，和「G2 后 90 天」对得上
- 计费模式：**只剩 PAY_PER_EVENT（PPE）一种可选**。
  全站 API 普查 44,676 个 Actor：`PAY_PER_RESULT = 0`。官方博客 2026-04-14 自述已把 2,000 个 Actor
  从 pay-per-result 迁到 PPE；monetize 文档与 pricing FAQ 也只列 Pay per event / Pay per usage。
  RENTAL 同步退场：4 月 1 日起不能新建，**10 月 1 日彻底废止**，剩余 Actor 强制迁移。
  → 新人现在没有选择题，只能 PPE。距 10 月 1 日约 2 个月，**不要碰 rental**。
- 政策风险：**不是"可能变"，是一年内已经变了两代**（PPR 废除 + RENTAL 废止）。
  法律条款 §10.1（2026-02-20 更新）里还写着 Pay per Result——条款滞后于产品，以 API 与产品文档为准。
  不是账号级封禁风险，但代码要按"计费模型还会再变一次"来写：**定价/计费逻辑与抓取解析逻辑分离**。

> 选它的三个结构性理由：
> 1. 代码在平台上跑 → **盗版不了**
> 2. 平台代收费、代导流 → 不用建收款也不用做营销
> 3. 同一份逻辑可复用成 p13 付费 MCP Server → 一次开发两个入口
>    **限制**：Store Publishing Terms §4.2 禁止在 Actor 内或 README 里推广、链接任何站外产品。
>    所以这条只能是**代码层复用**，不能做 listing 层互相导流。

## 单位经济
- 定价模型：PPE（按事件计费）
- 单价：**$0.003/条**（= $3/1,000 结果）
- 边际成本：**约 $0.00001/条量级**。实测依据：纯 HTTP 200，不需住宅代理、不需无头浏览器；
  详情页 209 KB，数据中心代理已含在 CU 内。成本比单价低约两个数量级。
- 毛利：**成本转嫁给用户时** `0.8 × revenue`；**自己吸收成本时** `0.8 × revenue − 平台用量成本`
- 到 $500/月 需要多少调用量：`500 ÷ (0.003 × 0.8)` = **约 208,000 结果/月**

### 定价与「区间上半段」规则冲突（已知偏离，不静默处理）

本文件上面写的规则是「单价必须落在 $1–10/1,000 的上半段」。**实测市场不在上半段：**

| 竞品 | 30 天用户 | 每结果价 |
|---|---|---|
| clearpath/welcome-to-the-jungle-jobs-api | 117 | **$0.00299** |
| shahidirfan/Jungle-Job-Scraper | 37 | $0.00099 |
| logiover/welcome-to-the-jungle-jobs-scraper | 28 | 未设结果价 |

领先者 $2.99/1,000 且已握有绝大多数用量。作为零评分新入场者定价 $5/1,000 卖不动。
**取 $0.003 与领先者持平**，靠「不要 cookie / 免登录 / 有静默失败检测」区分，不靠低价。
这是对规则的**有意偏离**，理由是实测数据；规则本身不改。

### 这门生意的规模上限（先看清再投入）

208,000 结果/月 才到 $500/月。整个 WTTJ 赛道 4 个竞品 30 天用户合计约 182。
**即使做到该细分第一，也大概率到不了 $500/月。** p01 的真实作用是验证
「平台带买家、无需自我营销」这一条被 20 个候选共享的前提，不是靠它本身赚到目标金额。

官方条款 §10.2 的算例：定价 $5/1,000 events，用户跑 1,000 次 → revenue $5，
平台用量成本 $0.5 记在开发者这侧 → **开发者实得 $3.50**（不是 $4）。

### 市场价格区间与代理成本相撞（这决定选题，不是决定优化）
市场锚点（Apify Academy 官方原话）：*"most prices on Apify Store range between $1-10 per 1,000 results"*
→ 真实价格带 = **$0.001 – 0.01/条**。

平台住宅代理 **$8/GB**（Scale 起 $7）。按每条结果约 200KB 估，纯代理成本约 **$0.0016/条**。

| 定价 | 代理占分成比例 | 结论 |
|---|---|---|
| $0.01/条（市场带顶部） | ~20% | 加上算力仍有毛利 |
| $0.001/条（市场带底部） | **>100%** | 做多少亏多少 |

**市场价格带的底部，正好是我这张表的亏损端。** 两条硬结论：
1. **平台成本必须转嫁给用户**，否则那 80% 是假的。
2. **不能在价格带底部竞争**。要打 $0.001/条的价，只有"不需要住宅代理、不需要浏览器渲染"的目标才可能。
   → 需要住宅代理 + 完整浏览器渲染的目标，在 PPE 下不可行，选题必须排除。

买方成本结构（影响用户愿不愿意跑）：Free $0（含 $5 预付额度，不结转）/ Starter $29，CU $0.20；
Scale $199，CU $0.16；Business $999，CU $0.13。1 CU = 1 GB RAM·小时。SERP $2.5/1,000（Scale 起 $1.7）。

### 收入基线：查不到可信数字，这本身是结论
上一版这里写的"新 Actor 三个月约 64 用户 / 约 $200 一个月，独立可验证"——**撤回，那个"可验证"是错的。**
调研结论：**Apify 渠道之外不存在可独立追溯的开发者 MRR 数据。**

能拿到的只有两条，且都要打折看：
- 唯一具体数字 [A 但有保留]：某开发者首个 Actor 上线次日"已经有用户和收入"、"一天赚一美元"。
  第一手引语，但发在 Apify 自己的推广博客上，且此人是 $1M 挑战赛获奖者，选择偏差明显。
  反过来说，**$1/天 这个数字小到不像编的**，正因为没被吹大才更可信。
- 最好的案例作者明确拒绝公布收入（"I'm not going to post revenue here"），但给了**收入形状** [A]：
  首个 Actor 上线后**整整一周零 run**；1–2 月周 run 个位数；3–4 月首次出现两位数用户、
  "收入开始有意义但不稳定"；5–6 月目录交叉发现效应起来；6 个月后 98 个 Actor / 2,500 总用户 / 855 MAU。

→ 规划口径：**按"首月可能一个 run 都没有"来设期望**，不按任何月收入数字规划。
  一周零 run 是正常，不是失败信号。

### 收款摩擦（直接影响 G3 怎么算过）
条款 §11 [A]：
- 提现前**必须完成 KYC**（政府身份证 + 地址证明 + 税务文件 + 受益人信息）。未验证满 12 个月 → 收入作废。
- 最低提现额：PayPal **$20**，其他方式 **$100**。连续 12 个月低于门槛 → 作废。
- Actor 处于 Faulty 状态期间**不累计任何收入**（§11.3）。
- 引导用户走站外付款 → Actor 直接封（§11.6）。

→ **G3「陌生人首笔付款」被这条切成两半**：收入产生（快）vs 钱到账（要 KYC + 攒到 $20）。
  哪个算过关，属于闸门定义变更，写进 `DECISION_LOG.md` 再改，本文档不自行改。
→ 立刻要做的事：**现在就做 KYC**，不要等有收入了才做。

## 最危险假设

### 上一版的假设：已判定，未被证伪（2026-08-09）
**「Apify Store 站内搜索能带来真实的自然发现流量」→ 判定 [B] 强间接证据，不是 [A]。**

最硬的一条是结构性反推，不依赖任何人的说法：Store 里存在**零评分但有真实活跃用户**的 Actor
（某目标站头部 Actor：30 天 117 活跃 / 472 总用户 / **0 条评价**；另两个目标站头部同样 0–1 条评价）。
零口碑 + 无站外营销，用户只可能是**在站内搜到或翻到的**。
辅证：某 Actor 30 天内月活 37 → 346；另一开发者首个 Actor 上线次日即有用户。

诚实的评级是 [B]，不是 [A]：**没有任何第一方文档直说"Store 搜索是发现渠道"**，
上述都是从数据形状反推的。按上一轮承诺，只有落到 [C] 不可核实才作废 p01 排位——
现在是 [B] 强间接，**p01 排位维持，D-001 不标 REVOKED**。

### 现在最脆的一条（替换上面那条）
**假设：单个 Actor（没有目录规模、没有历史评分）也能拿到自然流量。**

上面那批证据有个混淆变量：最好的案例是**98 个 Actor 的目录**，作者自述交叉发现效应到第 5–6 个月才起来。
"98 个 Actor 有流量"推不出"第 1 个 Actor 有流量"。如果自然流量实际来自目录规模，
那 p01 的正确形态就不是"做一个精品 Actor"，而是"做几十个"——**工作量和被动性的假设全变**。

- 如果它是假的：p01 不归零，但退化成"要铺量才有流量"，与 WIP=2 直接冲突，需要重新评估排位。
- **最便宜的证伪动作**：上架后 30 天内，看有没有 **≥1 个陌生人 run**（只看 run，不看付款）。
  不写额外代码，平台自带统计。
- 多久能得到答案：G2 后 30 天。
- 证伪了怎么办：**不靠加 Actor 数量抢救**（那是把假设当结论）。先判断是选题错还是单 Actor 发现机制不成立，
  再决定换选题还是把 p01 整体降级。

## 放弃条件
- G2 后 **90 天**内没拿到 G3（陌生人首笔付款）→ 杀掉，不续命
- **G2 后 30 天内 0 个陌生人 run** → 最危险假设被证伪，按上面那节处理，不等 90 天
- 目标站点上反爬导致月维护 > 6 小时且无法通过改代码降下来 → 杀掉
- 抽成超过 30%，或 PPE 也被废止/改造得无法按次收费 → 重新评估
  （"取消按次计费"这条已经部分发生过：PPR 废除、RENTAL 10 月 1 日废止）

## 维护面
- 必须介入的情况：目标站点改版 / 反爬升级 / 平台 SDK breaking change / **平台条款规定的响应义务**
- 预计月维护：2–4 小时
- 这个维护量是**纯负担，不是护城河**。

### 平台强制义务（这几条和 G4「月维护 < 2 小时」的精神冲突，必须先看清）
Store Publishing Terms [A]：
- §7.1 Apify 对所有 Store Actor **定期自动跑测试**。
- §8.1 测试失败 → 标记 "under maintenance" → **超过 30 天未修 → 废弃并/或下架，无补偿**。
- §9.1 / §9.2 用户报告的问题须在 **14 天内**处理；标 "urgent" 的邮件须在 **3 个工作日内**回。
- §11.3 故障期间**不累计收入**。
- §9.5 用户举报后，Apify 可**不通知、不给理由直接下架**（竞争对手举报是真实风险）。
- §2.1 名称与 README 不得用第三方商标/logo/易混淆名称，且**必须显著声明 "unofficial"、无隶属关系**。
- AUP §2.1.12 禁止"Apify 认为不道德或不可取的任何其他活动"——纯自由裁量。§3.1 可不通知封禁，不保证申诉。

→ **结论：p01 永远不可能完全无人值守。** 3 个工作日的邮件 SLA 意味着不能一个月不看邮箱。
  这直接影响"堤坝修好后人工不参与"的定义，属于闸门定义问题，
  写进 `DECISION_LOG.md` 讨论后再定，本文档不自行改 G4 标准。

### 绝不登录（红线，同时挡三种风险）
第一个 Actor **绝不要求 cookie / session / 账号密码**。
调研没找到任何"因登录抓取被 Apify 下架"的记录，但市场自己形成了规范——
在售同类 Actor 的卖点直接写着"never asks for cookies"、"no login required"、
"竞品要你的已登录 session，那意味着永久封号风险"。
真实风险不是平台封我，是**要了 cookie 会导致用户自己的目标站账号被封，然后回来给 1 星**。
一条红线同时挡掉：合同违约风险 + 评分风险 + 客服负担。

> 修正记录（2026-08-09）：先前写过"维护量是护城河，目标站改版会淘汰不维护的竞争者"。**撤回。**
> 该说法会诱导选题往难维护的目标走，方向是错的。护城河在**按次计费不可盗版 + Store 排位 + 先到者优势**，
> 与维护量无关。选题应优先选**低维护**目标（受外部标准约束的数据出口，格式不因设计改版而变）。

### 提取层的工程要求
- 绑**语义锚点**（JSON-LD 字段名、schema.org 属性、API 字段名），**不绑 CSS 选择器**。
  这一条对维护频率的影响可能大于其他所有因素之和。
- 失败告警必须能区分两种情况：**结构变更**（站点改版，改解析）vs **反爬拦截**（被封，改策略）。
  混在一起会导致每次告警都要人工判断，直接破坏被动性。
